# JustEnoughMods Project Rules

- Extend native mod interfaces instead of replacing them unless the user explicitly approves that exact redesign. Native villager trading layout/offer list/slots/restocking and Xaero GUI/controls/waypoint appearance are protected; Coins change currency presentation/payment, the Market Buyer opens a native trading window without chat, and optional JEM map layers must remain unobtrusive and hideable. The separate JEM-owned SMP GUI is not automatically reverted by this rule.
- Resolve current behavior from `AGENTS.logic-locks.md`, the owning `Docs` source and module source; old Codex chats, reports, plans, live-profile files and installed JARs are diagnostic evidence only.
- Before every task, run `python tools/jem.py status` from the project root or `python ../tools/jem.py status` from `Server`; never replace the immutable release baseline during ordinary work.
- For an explicitly requested overnight gameplay QA run, use `.agents/skills/jem-overnight-player-qa/SKILL.md`; its local testing scope does not authorize MineRENT/stable deployment or gameplay launches during ordinary tasks.
- Before touching modded gameplay, items, blocks, mobs, recipes, gear, biomes, loot, economy, progression or any related Java/Mixin/KubeJS/datapack/config/mod dependency, load and follow `.agents/skills/jem-registry-keeper/SKILL.md`. The mandatory order is Atlas lookup -> before-change impact scan -> implementation -> same-task `Catalog/changes` history/effective update -> Atlas validation. Original facts stay in `Catalog/registries`, JEM rules stay in `Catalog/changes`, and calculated behavior stays in `Catalog/effective`; never create a competing registry or silently change gameplay without a matching impact record.
- When the user says that the session is a continuation of the update or uses equivalent wording, load `jem-update-continuation`: continue from the freshest clean `Client`, keep `versions/JustEnoughMods` and the release baseline unchanged, and accumulate work for a later explicit MineRENT release.
- Route Forge code, integration, networking, performance and packaging through `minecraft-forge-lab`; new gameplay, progression, bosses and encounters through `minecraft-forge-feature-designer`; visual assets, GUI rendering, models, textures, animation, particles and sound through `minecraft-visual-authoring`; runtime cleanup and conflicts through `minecraft-modpack-auditor`.
- Preserve the ownership matrix in `Docs/DEVELOPMENT.md`: one gameplay fact has one canonical owner, adapters translate native signals, and no module reconstructs or duplicates another module's state.
- Before integrating an installed mod, inspect its exact installed version, registrations, configuration and real source or bytecode; reuse its native API, signal and assets before adding JEM code, and never invent an API from memory.
- Before declaring a minimal client update sufficient, compare every owning mod JAR for newly exercised network channels against the deployed server and include the exact matching JAR when the client may be older, because datapacks and compatibility adapters cannot satisfy Forge channel-version handshakes such as `ic_air:main`.
- Prefer the least invasive extension route: data/config/tag, public API or Forge event, isolated adapter, accessor/access transformer, then a narrow Mixin only when earlier seams cannot express the requirement.
- If current assets or tools cannot produce the requested quality, do not improvise a weak placeholder; identify the exact missing concept, source asset, format, license, MCP/tool or user action and explain precisely what must be provided.
- Never ship bulk NPC dialogue generated by neutral narrator TTS or pitch/EQ variants of one voice; first obtain user approval for expressive in-game audition clips with distinct character, emotion, rhythm and pauses, because the Edge TTS villager set was rejected as monotonous and artificial.
- Villager auditions must sound like brief playful Minecraft NPC chatter: casual native Russian, dry comic timing, clear pronunciation and compact phrases without anime/dorama acting, breathy delivery, sighs, moans, dramatic pauses or grave fantasy narration, because the serious Qwen VoiceDesign auditions were rejected as foreign-sounding and overacted.
- Villager dialogue is text-only: keep the localized three-second HUD subtitle and do not add speech audio, mouth animation or speaking body animation, because the user rejected both generated voice pipelines and explicitly chose pure text.
- Villager reactions use one local attention scene at a time: a higher-priority incident may interrupt a lower-priority line, while equal or lower events wait for the active scene and its silence window; threats outrank player actions, routine states and ambient speech, because independent per-event cooldowns made villagers discuss work and night during attacks and caused unreadable HUD replacement storms.
- Villager subtitles must remain fully readable when chat is open: render the complete wrapped first speaker line above the chat for three seconds and never let chat cover or suppress it, because chat is part of normal multiplayer play.
- Villager multi-speaker scenes must label every HUD line with the custom name or localized role and a stable scene ordinal, while solo reactions remain unlabeled, because otherwise two- and three-villager dialogue looks like one villager speaking unrelated lines.
- Keep server authority for gameplay state, validation and results; clients render synchronized presentation and never become a second authority.
- Diagnose the complete cause chain and fix its owner; do not hide invalid state, missing assets, compatibility faults or lifecycle errors behind fallback behavior.
- Do not create, retain or run automated tests, test fixtures or runtime test scenarios in this project, because the user explicitly rejected testing and requested deletion of all tests during the architecture revamp.
- Do not run Gradle builds, launches, linters, formatters or static analysis unless the user explicitly requests that exact activity in the current turn.
- Before every user-requested push, finish and synchronize every task-owned source, clean Client, Server, documentation, release-state and other version-controlled file first; if any in-scope tracked file changes after that push, commit and push the newer complete state again, because GitHub must always end on the freshest task-complete snapshot rather than an intermediate pre-build or pre-deployment state.
- `Client/ManagedPack` is the canonical full AutoModpack source, while `Client/JustEnoughMods` is the clean bootstrap-only installer template; `Mods` contains source projects, and `Server` plus TLauncher profiles are runtime targets. Follow `Docs/DEVELOPMENT.md` for reobfuscation, deployment, stable synchronization and ZIP rules.
- Run every local client-side development and JEM Pack Sync test only in the TLauncher profile `test jem`; never modify or launch the stable `JustEnoughMods` profile during local testing, because the user keeps it as the untouched original client until an explicit release deployment.
- The stable `JustEnoughMods` profile may receive only the explicitly supplied matching `mods/jem-bootstrap.jar` before native recovery; do not raw-copy gameplay, config, or managed pack files into it, because the user requires the bootstrap itself to perform the same clean first-install path used by friends.
- When the user will manually test a bootstrap in the stable `JustEnoughMods` profile, do not mutate, repair, move, remove, or preseed its AutoModpack runtime cache or state; prepare the standalone JAR elsewhere so the user's launch exercises the same untouched first-install path as friends.
- A normal successful MineRENT deployment is one client-and-server release boundary: publish the same changes to clean `Client`, stable `JustEnoughMods` and the timestamped friend point-update with exact replace/add/delete instructions, then record the local release date/time and promote that Client snapshot as the baseline from which every later task forms the next update. When the user explicitly requires a server-only MineRENT update and investigation proves existing clients already understand every registry and network contract, deploy only server-owned artifacts, do not touch `Client`, stable profiles, friend packages or the client release baseline, and record the separate server release in `CHANGELOG.md`, because forcing an unnecessary client package would violate the requested release boundary.
- When the user asks to restart MineRENT immediately after authorizing a proven server-only source change, treat the request as applying that change: build and upload its server artifact before restarting instead of restarting the stale deployed JAR, because a restart alone cannot activate source edits.
- Never include an active local JEM Pack Sync test generation, its `Server/local` restoration state, test-only JARs, test configs, or test mod substitutions in a MineRENT deployment; before any MineRENT release, restore the local server runtime, revert the test generation, and restage the host pack exclusively from `Client/ManagedPack`, because local AutoModpack transport tests are not release inputs.
- Read the live MineRENT `Сеть` page before giving connection details: `ForeverSMP.minerent.io:25565` is the primary address, while the numeric fallback uses the separately displayed dynamic port such as `87.228.57.196:31604`; never combine the resolved IP with the domain's port because MineRENT routes them differently.
- Every friend/shared point-update ZIP must include the complete current `Client/ManagedPack/kubejs` tree even when files are unchanged from baseline, because recipients may not already have the scripts, data, configuration, examples, or localization present in the maintainer's client.
- Every new friend/shared point-update must be a cumulative remake of the immediately previous point-update: copy forward every still-current file from that package, then let current `Client/ManagedPack` files override matching paths, because recipients may install only the newest ZIP.
- When the user requests a point-update re-release based on a named earlier ZIP, publish the union of both packages with the newer package overriding every coincident path, because recipients must receive earlier release changes that are absent from the newer delta.
- Keep one current source per category: engineering and distribution in `Docs/DEVELOPMENT.md`, each event in its single `Docs/events` file, SMP behavior and visuals in `Docs/smp-gui/README.md`, and console operations in `Docs/SERVER_COMMANDS.md`.
- Update `CHANGELOG.md` for every user prompt that changes the project, recording what changed and why, and explicitly distinguish the user's requested behavior or supplied technical direction from implementation details chosen independently by Codex, because the project history must preserve who made each product and technical decision.
- Use the global `evidence-first-debugging` skill as the sole defect-investigation procedure. Record its established result in `CHANGELOG.md` as `Bug / Client, Server, or Both Sided / concrete root cause / status`; use `in testing` before user approval and `resolved` only after approval while naming the exact resolution mechanism.
- Use external repositories as tools or references only under the decision rules in `Docs/DEVELOPMENT.md`; do not copy code or assets without compatible licensing and do not add runtime libraries without a concrete feature contract.
- Boss Raid eligibility is derived from the canonical registered boss profile, historical defeat and registered structure arena; never require or recreate a manual entity-type allowlist, because every structural boss must be raid-capable without per-boss enrollment.
- Structure ownership, territory boundaries, entry, safe arrival and safe exit belong to the ordinary hosted boss encounter lifecycle; Boss Raid may add only raid scaling, reinforcements and reward distribution, because event-specific arena handling makes normal boss fights behave inconsistently.
- Structural boss placement and revival repair must apply to every registered boss through the shared arena lifecycle and must prefer a sheltered in-structure floor before any exposed roof surface, because entity-specific roof fixes leave the same failure active for every other boss.
- Active hosted boundaries must classify and save safe positions using the player's full collision box with clearance, never only the feet block position, because an edge-intersecting saved coordinate traps the player in repeated correction teleports.
- Blood Moon boss debuffs reuse vanilla or installed-mod effects first; Armor Penetration and Epic Fight/Nightfall locks are timed player states, and every blocked action names the active debuff because silent denial looks like broken controls.
- After Blood Moon combat starts, every player may freely cross its territory, but all players outside the current active participant set, including eliminated participants, are completely ineligible for event-mob targeting, Warden anger, vibration investigation and navigation because the user wants safe spectators inside the arena.
- Keep Create train speed native and do not apply JEM transport speed caps to trains, because the user explicitly restored upstream train balance for this update.
- Do not include Saints Dragons or Saints-specific JEM integration in JEM distributions; retain DragonLib only while another installed mod requires it, because the user explicitly rejected Saints Dragons.
- Keep JEM SMP and shared-server gameplay physically dedicated-server-only: integrated singleplayer must not register its commands or listeners or apply its common gameplay Mixins, while the installed client retains only registry, network, screen and rendering compatibility needed to join ForeverSMP without another download, because the user requires native singleplayer with zero server-owned runtime behavior.

- Never directly synchronize clean Client files into the gameDir of an active AutoModpack profile; native AutoModpack exclusively owns its managed installation and generation commit, because mixed raw-copy/native ownership broke captured-source validation and caused repeated update prompts.

- Globally share only explored Xaero terrain and authoritatively discovered boss locations; native personal waypoints, homes/bases, labels/colors/groups/settings and death points remain creator-private, because the user explicitly replaced the previous shared-waypoint policy and requires clean-client recovery without leaking personal map data.
- Keep every registered structural boss AI-, target-, damage-, boss-bar- and music-dormant until the canonical hosted encounter Start, and treat actual participant death as immediate elimination without hidden lives, health restoration, immunity or teleport-to-boss, because proximity must never start presentation or combat and the user requires “dead means dead.”
## After every project-changing prompt

1. Inspect the current branch, tracked and untracked diffs, staged files, remotes and local-only commits before editing. Separate the current prompt's files from unrelated work and preserve all unrelated changes in place; use only explicit paths for any staging or temporary preservation and never use broad staging.
2. Work in the current checkout and current intended branch. JEM has no per-prompt task-branch workflow: do not create a task branch or worktree, and do not switch branches, rebase or rewrite history merely to deliver a prompt. Fetch the configured remote before delivery, inspect divergence, preserve every local commit and integrate remote history only when it is safe and actually required.
3. Finish the complete consequence chain for the prompt across canonical module source, `Client/ManagedPack`, local `Server`, Atlas, owning documentation, release metadata and `CHANGELOG.md` wherever each surface applies. Never substitute a runtime file or installed JAR for its source owner, and never include credentials, world saves, personal runtime data or unrelated local changes.
4. Treat this standing rule as authorization to build only the production artifacts required by the prompt and to synchronize their exact fresh outputs into the ordinary local `Server` and `Client/ManagedPack` according to `Docs/DEVELOPMENT.md`. It does not authorize Gradle tests, automated verification, gameplay QA, MineRENT deployment, stable-profile mutation or release-baseline promotion.
5. After every managed client add, replacement or deletion, run `python tools/jem.py stage-pack-sync`, inspect native `/jempack preview`, and publish through native `/jempack publish` so the ordinary local server exposes a fresh normal AutoModpack generation that clients can download. Confirm with `python tools/jem.py status` that the staged and published manifest hashes match; never claim the client generation is fresh while `packSyncPublication.published` is false.
6. The ordinary local dedicated server may be started or restarted only as needed to install the prompt's server artifacts and complete the native AutoModpack preview/publication above. Do not launch a disposable/test server, a gameplay test, or the `test jem` client unless the user explicitly requests that exact activity. Preserve worlds and stop/restart cleanly when a runtime restart is required.
7. Review the final diff against the fetched remote/current branch base and run only checks permitted by these project rules. Do not claim that any unrun build, test, launch or player acceptance passed.
8. Update `CHANGELOG.md`, stage only exact current-prompt paths, create a short natural professional commit with no AI/tool attribution or co-author trailer, and push the current intended branch with its upstream after every completed project-changing prompt unless the user explicitly opts out in that prompt. Do not create a PR/MR unless requested.
9. Use a normal push. If remote history moved, fetch and integrate it without discarding local or remote work; never force-push unless the user explicitly authorizes that exact force-push in the current prompt. If delivery cannot be completed safely, preserve the work and report the exact blocker instead of bypassing it.
10. Verify that the remote branch points to the delivered commit and report the branch name, short commit hash, local Server synchronization state and native AutoModpack publication state. If any in-scope tracked file changes after the push, commit and push the newer complete snapshot again so GitHub ends on the freshest prompt-complete state.
