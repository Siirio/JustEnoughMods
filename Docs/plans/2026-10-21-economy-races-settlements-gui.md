## Что уже установлено по исходникам

1. `PhysicalCoinItem` уже разрешает стак до 64. `CoinProvenance.issue` записывает уникальные Lot/Operation UUID в NBT, поэтому монеты разных выпусков не совпадают для vanilla stack merge. Исправление одного `stacksTo` проблему не решит.
2. В CurrencyCore `item_policies.json` продажа алмаза сейчас равна 9188437/1000000 медных за штуку; покупка — 3000/64. Запись связана с пересчётом recipe buyback. Следовательно, нужно исправлять владельца цены и её генератор, а не только отображение девяти медных.
3. `RaceRules.GUARDIAN_COOLDOWN` имеет значение один Minecraft-день. В `RaceTraitRuntime` сопровождающий голем выбирает ближайший `Mob instanceof Enemy`, что не включает атакующего игрока.
4. `RacialSpells` регистрирует скалк-способность в школе Eldritch; `RacialSpell` вызывает общие условия Iron's Spellbooks. Это направление расследования сообщения о непонимании, но точная причина ещё не доказана.
5. В проекте уже существуют `DeathHistory`, `SmpActions`, `SettlementMapClient`, `SettlementMapScreenMixin`, `SettlementRuntime` и Jade-интеграция Settlements. Следует расширять текущих владельцев.
6. Ранние запуски `jem.py status` завершались PermissionError при чтении stableClient; профиль не исправлялся. При текущем дополнении плана read-only status завершился успешно: release delta0, stable drift0, publication51 уже опубликована и staged/published SHA1 совпадают. Это наблюдение существующего состояния, не сборка/синхронизация/публикация этой задачей и не проверка работающего MineRENT.
7. `DeathHistory.open` уже строит выбор сохранённых смертей и вызывает `teleport(player, death.id())`; `ServerData.addDeath` хранит записи от новой к старой с пределом `ServerConfig.HISTORY_SIZE`. `SmpActions.DEATH_HISTORY` вызывает этот экран. В просмотренной регистрации `JemServer.registerCommands` есть `/home`, но `/death` отсутствует. Перед исправлением всё равно проверить полную регистрацию/видимость/client dispatch.
8. `/home` уже принадлежит `smp/events/HomeTravel.java`, использует личную respawn point и BedBlock/RespawnAnchorBlock. Это owner для `/home all`; второй home storage не нужен.
9. Приложенный аудит относится к указанному автором коммиту4b4b04a и прямо не подтверждает MineRENT. Его таблицы цен/охвата — предоставленные наблюдения для перепроверки, не состояние текущего runtime. В этой задаче read-only lookup подтвердил source константы400/10000 обычных дневных выплат, CENTRAL_RESERVE60000, OPERATIONS20000, стартовую выдачу2000 и Coin-налог из OPERATIONS; остальные числа аудита не объявляются проверенными.

### 6.1. Доход от счастья вместо налоговых ставок

Прямые пользовательские якоря из дополнения: убрать выбор ставок0/5/10/15%; жители платят по счастью; **10жителей при100%=4Gold,20жителей при100%=8Gold за Minecraft-день**. Вопрос о печатном станке не является разрешением на бесконечную эмиссию.

Владельцы: `JEMSettlements/payroll/DailyTaxService.java`, `payroll/SettlementEconomyConfig.java`, `currency/SettlementCurrency.java`, `town/SettlementSavedData.java`, текущие happiness/membership owners и treasury projection.

- [ ] Удалить выбор ставки из расчёта, UI и server actions. Legacy ставка не управляет новой выплатой; старый пакет не должен превратиться в другое действие. Баланс казны/старые receipts сохраняются.
- [ ] Предложенная в приложенном ответе линейная формула — **планируемый механизм Codex для выполнения пользовательских якорей**: `dailyDueCopper = Σ(40 × H_i / 100)`, `H_i` — каноническое счастье каждого назначенного жителя0..100. Не создавать второй happiness owner.
- [ ] Примеры:10×100%=400Copper=4Gold;10×75%=300Copper=3Gold;10×50%=200Copper=2Gold;20×100%=800Copper=8Gold;20×50%=400Copper=4Gold за Minecraft-день. Считать рациональную сумму и сохранять дробный остаток; не терять его по каждому жителю.
- [ ] Отдельный comfort bonus/процентную ставку не прибавлять поверх новой формулы; питание/уют уже влияют на текущее счастье. Не вводить скрытый satiety multiplier, нарушающий якорь100%, и не менять сами факторы счастья/PatPat этим пунктом.
- [ ] Один житель — одно поселение/один due snapshot за период. Смена owner, смерть, unload/recreation и restart/catch-up не дают повторной выплаты; сохранить settlement/day idempotent receipts. Не вводить произвольный cap числа учитываемых жителей/расчётного дохода.
- [ ] **Расчётный доход и оплаченный доход различаются.** Реальный перевод из конечного фонда, пополняемого поступлениями рынка по1.1, идёт в **казну поселения**, не в карман владельца. Coin ledger остаётся денежным owner; standalone emerald-mode не получает молча новую Coin emission или курс.
- [ ] Предложенное приложением и выбранное Codex для плана поведение при нехватке: пропорционально распределять доступный фонд между всеми допустимыми поселениями одного периода, а не платить первому до исчерпания. Округление детерминированное, итог не больше фонда, повтор тика не платит снова. Это пока предложение реализации, не проверенный код/отдельно утверждённая финансовая политика.
- [ ] Хранить due/paid/shortfall отдельно. Недоплата не превращается сама в бесконечный долг, повторную полную выдачу при restart или эмиссию. Рабочее предложение — доступная выплата за период, без автоматического накопления безусловного долга; перед реализацией закрепить правила переноса.
- [ ] В существующей treasury UI вместо ставки показать расчётный/реально выплаченный доход и нехватку фонда; ненулевые Coin denominations и Minecraft-дни, **без редизайна `/smp`**. Обновить DESIGN_JOURNAL и owning economy doc вместе с реализацией.

**Печатный станок:** безусловное периодическое зачисление превратит рост населения в эмиссию. Перевод из конечного фонда не создаёт деньги, но большой due способен быстро исчерпать фонд; нужны реальные поступления/оборот и честное отображение недофинансирования. Снятие торговых квот не разрешает обход этого ограничения.

## Приёмка и открытые решения

До отдельного разрешения здесь нет builds, tests, launches или установки; runtime-пункты остаются критериями будущей ручной приёмки, а не выполненными проверками.

- Пограничные денежные случаи: старые монеты, полный/частичный инвентарь, split/merge, повтор запроса и недоступный резерв не теряют/не создают стоимость.
- Публичный ящик: два одновременных посетителя, выход первого и старые остатки не смешивают владельцев.
- Смерть: `/death` и профиль ведут в выбор до трёх последних собственных мест смерти; выбор переносит к правильной безопасной записи, не в races.
- Домой: `/home all` включает ближний состав в радиусе1блока и ridden vehicle tree; большой mount и пассажиры помещаются рядом с кроватью. Невозможное размещение не оставляет половину группы в другом измерении. `/spawn` не добавляется.
- Поселения: чужой колокол/житель не присваиваются, новый житель приходит сам, map drag имеет только один активный owner.
- Экономика:40стартовых выдач имеют конечное финансирование; обычных дневных JEM caps нет, крупный заказ проверяет права/вместимость. Доход10×100%=4Gold и20×100%=8Gold за Minecraft-день — расчётный; выплата не больше фонда и не зависит от очередности городов.
- Xaero: один широкий двухстрочный пункт без разделительной линии/нулевых монет; один action для одной актуальной server quote.
- GUI: дизайн `/smp` сохраняется; необходимые русские подписи, tooltip/dropdown/focus и суммы помещаются без пересечений.

Открытые числовые решения: новая цена Починки, сравнительные доходы урожая/золота/дропов, начальное конечное распределение фондов для40игроков и доля рыночных поступлений на налоги. Алмазный якорь и доход10/20жителей при100% заданы пользователем; линейная интерполяция и proportional funding явно помечены как предложения реализации. Точную причину проблем древнего стража/скалка установить по owning source/installed JAR, не угадывать. Существенную оставшуюся неоднозначность уточнять конкретно. Ни один пункт не разрешает runtime mutation или запуск игры.
