## PART 1 — House Viewer: Camera-Aware Volumetric Cutaway

### 1. Fix wall removal direction

Currently, the House Viewer does not correctly remove walls from the side the player is looking at.

Expected behavior:

1. Detect the current 3D preview camera position and viewing direction.
2. Determine which blocks are between the camera and the house interior.
3. Remove only the obstructing blocks on the camera-facing side.
4. When the camera rotates around the house, dynamically update the cutaway.
5. Never remove the opposite wall simply because it shares a particular world axis.
6. Roof sections must also be handled when the camera is looking downward.

Example:

- Viewing from the north → cut away the north-facing obstruction.
- Rotate east → update the cutaway for the eastern viewpoint.
- View from above → reveal the room through the roof.
- View diagonally → remove the relevant obstructing corner volume, not an arbitrary complete wall.

Cutaway selection must be relative to the **preview camera**, not player world orientation or a hardcoded north/south/east/west direction.

### 2. Replace the current Layers behavior

I want a slider called **Просмотр внутрь** / **See Inside**.

Range: 0–10.

| Value | Expected behavior |
|---|---|
| 0 | Default complete house rendering, with no additional cutaway |
| 1 | Look approximately 1 block deeper through the obstructing side |
| 3 | A larger opening reaching approximately 3 blocks inward |
| 5 | A broad, clearly visible cutaway reaching 5 blocks inward |
| 10 | Maximum cutaway depth of 10 blocks, exposing as much relevant interior as possible |

The value represents maximum depth in blocks from the camera-facing surface, not a Y-level or the number of removed floors.

### 3. Spherical voxel cutaway

I do NOT want the current flat rectangular wall removal.

I want a **spherical or rounded volumetric cutaway formed from Minecraft block-sized cubes**.

Imagine cutting a rounded cavity into the front of the building to expose its rooms.

Requirements:

- All removed geometry must follow the Minecraft block grid.
- The resulting empty region should approximate a sphere or rounded excavation using individual block positions.
- Increasing the slider makes the cutaway deeper and wider.
- The opening should remain centered around the useful visible interior rather than randomly expanding.
- The opening should work from diagonal camera angles.
- Prioritize revealing beds, workstations, decorations, furniture and other relevant interior blocks.
- Never create real air blocks in the world.

Implementation guidance:

Use camera-space geometry or an equivalent voxel selection algorithm.

Determine the preview-visible surface and calculate a rounded cutting volume extending inward along the camera viewing direction.

Allow the effective opening radius to grow smoothly as depth increases, while keeping the specified slider depth as its hard limit.

The default state at 0 must retain the existing full-house view.

If the renderer uses a cached block model, rebuild or filter the visible geometry when the slider or camera orientation changes. Avoid rebuilding every frame unnecessarily.

### 4. Camera interaction

Keep and improve:

- Left-drag: rotate house
- Mouse wheel: zoom
- Right-drag: pan, if supported
- Reset View button
- Smooth camera rotation
- Sensible minimum/maximum zoom
- Consistent camera focus

Do not let the camera accidentally rotate the underlying Minecraft world.

The cutaway must update correctly during rotation without obvious flickering.

### 5. Preserve house recognition

The House Viewer exists to help players understand how a villager's home is recognized and what should be decorated.

Preserve the actual detected house boundaries and its existing validation logic.

Where data is available, make it possible to visually distinguish:

- Recognized house boundaries
- Beds and functional objects
- Existing decorations
- Missing requirements
- Current comfort versus saved comfort

Do not invent decoration scores or house requirements.

Provide hover tooltips explaining recognized objects and their contribution when supported by existing game data.

A cutaway should make the interior easier to understand, not hide relevant objects.

### 6. Performance and safety

- Rendering-only changes: NEVER modify real world blocks.
- Work for houses of different dimensions and shapes.
- Avoid scanning entire chunks on every rendered frame.
- Handle camera angles, missing blocks, large houses and unusual roofs.
- Keep the UI responsive when rotating and changing the slider.
- Avoid permanently invisible blocks when exiting the screen.
- Restore the original rendering state immediately when closing the preview.

## PART 2 — Recruit GUI: Complete UX Redesign

The existing Recruit interface is confusing, crowded and inconsistent.

Screenshot 4 is a visual reference for the desired direction, not a requirement to duplicate an existing texture exactly.

### 1. Visual style

Use a polished Minecraft-themed interface with:

- Wooden borders and panels
- Parchment-colored stat background
- Pixel-art icons
- Dark recessed inventory slots
- Consistent panel padding
- Clear visual hierarchy
- Correctly aligned text
- Pixel-perfect scaling

No modern flat web-app design, random gradients, smooth vector icons or blurry AI-looking assets.

Preserve native Minecraft visual proportions.

Reuse our existing GUI assets and shared components when possible. Create new compatible pixel-art assets only when necessary.

Use responsive/scaled positions, not fixed coordinates that break under different Minecraft GUI scales.

### 2. Recruit 3D preview

Left section:

- Render the actual recruit model.
- Include equipment, held weapons and armor.
- Keep readable recruit name and employment status.
- Allow model rotation by dragging.
- Automatically fit the character inside the preview frame.

The recruit preview must not overlap labels.

### 3. Replace plain stats with icons

Every important stat must have its own recognizable Minecraft-style pixel-art icon.

Use the following logical layout:

| Left column | Right column |
|---|---|
| ❤️ Current HP | ❤️ Maximum HP |
| ⚔️ Level | 🗡️ Attack |
| ☠️ Kills | 👢 Movement speed |
| ⭐ Experience | 🛡️ Armor |
| 🙂 Morale | — |

These emojis describe icon meanings only. **Use actual pixel-art assets in the implementation, not emoji fonts.**

Avoid redundant labels if the icon and tooltip already explain the value.

Important:

- Current HP and maximum HP must remain distinguishable.
- Show useful numerical units when available.
- Respect actual attribute modifiers.
- Do not hardcode a recruit's attack or speed.
- Format values consistently, e.g. `1.0`, not arbitrary precision.
- Provide a tooltip explaining each stat.
- Show progress bars only when they represent actual measurable progress.

All displayed values must come from actual game data.

### 4. Fix confusing recruitment payments

The current interface shows:

- An emerald icon and 120
- Another emerald icon and 20
- "За 7 дней"
- Another emerald inside the Hire button

This is visually repetitive and does not explain what the player is purchasing.

First inspect the existing recruitment/payment code and establish what each payment actually means.

If the values represent an initial hiring fee and recurring wages, display:

**Стоимость найма: 120 монет**

**Жалование: 20 монет каждые 7 игровых дней**

English:

**Hiring cost: 120 coins**

**Wages: 20 coins every 7 Minecraft days**

Use actual configured amounts instead of hardcoded example values.

Do not claim wages are recurring until the code confirms they are.

If there are existing wage timers, payment deadlines, arrears or employment conditions, explain them through contextual tooltips.

Use the JEM economy currency and correct coin denomination icons wherever the current integration supports them.

Do not introduce emerald payments if the JEM economy has already replaced them with coins.

Avoid displaying the same currency icon beside every repetition of the same price.

The primary action should simply read:

**Нанять / Hire**

The cost should be clearly visible once in the pricing section.

If the player cannot afford hiring, disable the button and explain the reason on hover.

If the recruit is already employed, show the appropriate management actions rather than a misleading Hire button.

### 6. Inventory layout

- Normal item tooltips

### 7. Localization

Both Russian and English must be supported.

Avoid mixed strings such as Russian descriptions paired with unexplained English controls.

Test layout with long Russian translations.

Do not truncate important information unless a tooltip provides the full text.
