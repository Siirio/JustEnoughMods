# Recruitment implementation audit — 2026-10-17

Evidence is current module source and inspection of the actual installed Forge 1.20.1 JAR bytecode (`javap -p -c`), metadata and configuration. This is a static audit, not gameplay acceptance. Paths are repository-relative; `S` below means `Mods/JEMSettlements/src/main/java/com/siirio/jemsettlements/`; native class names are under `com.talhanation.recruits`.

The three inspected Recruits files have identical SHA-256: `4b53c1b752e886ba10985aad2df30d668971810230eb77867e07428a21d1af7f`. The filename is corroborated by `META-INF/mods.toml`, not inferred from the screenshot.

JEM has no second independently registered soldier species or replacement combat AI. `S/compat/recruits/RecruitsAdapter.ownedBy` checks the native `AbstractRecruitEntity`. `RecruitRuntime.openManagement` calls the same native entity's `openGUI`; `RecruitHiringMixin` extends its `hire`; `RecruitCurrencyMixin` adapts native `CommandEvents.handleRecruiting`. Consequently “JEM recruits versus Recruits” compares the integrated experience against its upstream implementation, not two competing armies.

Guard Villagers is genuinely separate: its `tallestegg.guardvillagers.entities.Guard` extends `PathfinderMob`, with its own owner UUID, guard position, patrolling state, `GuardContainer`, `GuardInventoryScreen`, `GuardPacketHandler` and `VillagerToGuard`. It does not extend `AbstractRecruitEntity` and is therefore outside the inspected JEM Recruits adapter. This audit does not silently treat guards as hired JEM soldiers. Its detailed prices, recruitment eligibility and cross-mod targeting were not traced and remain unverified. No mod was deleted or disabled by this GUI work.

## Conflict findings and safe reuse

* **No duplicate JEM recruit entity registrations:** JEM adapts `recruits:*`. Do not remove Recruits as “duplicate”; the JEM integration depends on its actual entities, GUI and behavior.
* **One hiring and payroll currency owner:** active JEM authority replaces upstream item charging and upkeep; server-projected currency is used by the screen. Do not enable a second salary subsystem or calculate client-side balances. Without an authoritative quote, the dedicated-server screen waits rather than showing a guessed emerald fee.
* **One command-group owner:** `Infantry`, `Ranged`, `Cavalry`, `Ranged Cavalry` are the four native defaults created by `RecruitsGroupsManager`; custom names remain user data. Selecting one does not turn a recruit into a different class and has no invented equipment/training requirement.
* **One recruit inventory owner:** hire-screen slots are the player's inventory; hired management opens the existing native equipment screen. Changing the hire panel must not alter slot count, index, ItemStack storage or server click handling.
* **Territory is intentionally separate:** JEM settlement membership/assignment does not enable native Recruits claim protection; canonical default claiming is disabled. Actual existing world configs require read-only inspection before asserting effective runtime state.
* **Guard Villagers is a distinct possible coexistence surface:** canonical pack has its own guard entity/ownership/inventory; the sandbox does not. JEM's `AbstractRecruitEntity` checks exclude it. No same-ID collision was found, but targeting, faction relation, equipment transfer and guard-to-recruit conversion compatibility were not proven. Do not promise universal safe coexistence or automatically integrate guards into payroll.
* **Ordinary loyal recruitment can coherently coexist with JEM because it is the same native system plus adapters.** Runtime slots, click/stack behavior, disabled reasons, long translations, connection refresh and group selection still need actual user-authorized acceptance. This source audit alone cannot certify a running session.

Directly reuse native group management, formations, patrol routes, equipment, leveling and loyal combat AI: they already exist. Useful future work is exposing links to these native management screens from the settlement roster and clarifying their existing permissions. A Guard Villagers bridge would need an explicit product contract and separate adapter/ownership/payroll investigation. Do not add another recruit state model, copy AI, add training classes or introduce combat mechanics for this GUI request.

Recruits declares **All rights reserved** in its installed metadata. Guard Villagers declares **MIT for code, ARR for assets**. This change inspects bytecode and calls installed native APIs; it does not copy third-party source or artwork. The hire panel reuses Minecraft-owned runtime textures/icons and a JEM-authored parchment sprite, with source provenance below.

## GUI change evidence and limits

The old JEM `RecruitHireScreenMixin` appended quote rows to native labels without reserving their bounds. The native screen still drew item-price cells and hardcoded English statistics, causing redundant/conflicting presentation. The replacement suppresses only native labels/background, uses a 300×223 logical-pixel panel, preserves all native player-slot coordinates, retains the native hire request callback, and uses real native group data. Current/max HP have separate tooltips; attack now uses the modified `ATTACK_DAMAGE` attribute (native `getAttackDamage()` reads base value); movement speed is the modified raw `MOVEMENT_SPEED` attribute, not an invented blocks/second conversion. The actual recruit renders with native equipment and drag rotation; pose restoration belongs to vanilla `InventoryScreen.renderEntityInInventoryFollowsAngle`.

Owners: `S/mixin/RecruitHireScreenMixin.java`, `S/client/RecruitHirePresentation.java`; sprite `Mods/JEMSettlements/src/main/resources/assets/jem_settlements/textures/gui/recruit/parchment.png` comes unchanged from `Docs/settlements/assets/source/control-family-r1/exports/settlement_panel.png`, whose editable ORA, manifest and source provenance remain beside it. Wooden material uses native `minecraft:textures/block/dark_oak_planks.png`; semantic icons are native item/HUD sprites. No supplied reference pixels were cropped into production.

Current and target screenshots are preserved in `Docs/settlements/assets/reference/house-recruits-2026-10-17`. They guide wood/parchment, recessed slots and readable hierarchy; they are not after screenshots.
