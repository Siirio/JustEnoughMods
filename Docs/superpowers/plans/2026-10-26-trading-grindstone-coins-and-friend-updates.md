# План: торговля, точило, обмен монет и обновления друзей

Дата: 2026-10-26, Asia/Yekaterinburg

Статус: реализация в исходниках и локальная доставка завершены, пользовательская игровая приемка ожидается. Подтверждение сборки, Atlas, публикации поколения 83 и native применения в `test jem` записано в `Docs/releases/jei-trading-grindstone-coins-20261026.json`

**Цель:** показать доступный товар в торговле, добавить последовательное извлечение зачарований, упростить обмен монет и установить причины проблем обновления сборки и шейдеров у друзей

**Архитектура:** нативная торговля сохраняет своё окно и слоты. Economy остаётся единственным владельцем денег и обеспеченных монет. Извлечение зачарований расширяет обычное точило через серверный обработчик Compat. Доставкой сборки продолжает владеть нативный AutoModpack и отдельно обновляемый bootstrap

**Стек:** Minecraft 1.20.1, Forge 47.4.10, Java 17 для доменных модулей, существующий закреплённый upstream bootstrap

**Спецификация:** текущий запрос пользователя, два приложенных снимка и уточнение "Изменения сборки целиком". Разделы ниже сохраняют требования и отдельно помечают предложенные технические решения

## 2. Последовательное извлечение зачарований на точиле

### Требование пользователя

- Игрок держит зачарованный предмет и нажимает Shift + ПКМ по точилу
- Один отдельный клик снимает ровно одно верхнее зачарование целиком с сохранением его уровня
- У точила на землю выпадает зачарованная книга с этим зачарованием
- Возвращается 70% опыта, потраченного на снятое зачарование
- Порядок соответствует показанному списку сверху вниз. Пример: Эффективность → Прочность → Шёлковое касание
- Обычный ПКМ сохраняет нативное открытие точила. Начальная фраза про right click конкретизирована повторённым пользователем Shift + ПКМ

### Предложенный технический подход

- [ ] Сверить `minecraft:grindstone`, затронутые enchantment IDs и реальные установленные моды с Atlas. Найденные EasyMagic 8.0.1 и EasyAnvils 8.0.2 учитывать по их фактическим контрактам
- [ ] Использовать серверное взаимодействие с настоящим блоком и предметом в руке. Отсечь повторное исполнение через вторую руку и повторную доставку одного действия, не вводя произвольную игровую задержку
- [ ] Сверить порядок native tooltip с сохранённым списком зачарований. Не сортировать по алфавиту или registry ID. Если мод меняет отображаемый порядок, явно решить совместимость с его владельцем
- [ ] Сначала подготовить согласованную операцию снятия, ItemStack книги и возврата XP, затем зафиксировать её на сервере. Сохранить остальные зачарования, имя, повреждение, атрибуты и посторонний NBT предмета
- [ ] Новый обработчик разместить в `Mods/JEMCompat/src/main/java/com/siirio/jemcompat/feature/enchanting/` по существующим правилам регистрации событий. Это предложенный новый путь, сейчас такого владельца функции нет
- [ ] Не удваивать компенсацию через общий x2 XP pipeline. Согласовать выдачу с текущим `ExperienceRewardApi` WorldBossTiers и не допустить повторного возмещения одной стоимости

### Решения, необходимые до реализации этой части

Фактическую историческую стоимость каждого зачарования нельзя вывести только из его ID и уровня. Один предмет мог быть получен через стол, наковальню, книгу, торговлю, добычу или команду. Уровни опыта также не равны фиксированному числу XP points

Предложение для рассмотрения: фиксировать фактически списанный XP при применении зачарования, затем возвращать `floor(paidXp × 70 / 100)` один раз для снимаемой записи. Это предложение, не утверждённая пользователем новая система

- [ ] Согласовать семантику 70%: фактические XP points или иной явно выбранный пользователем расчёт
- [ ] Согласовать правило для существующих предметов без истории стоимости. Не приписывать им выдуманную оплату и не выбирать молча нулевой возврат
- [ ] Согласовать распределение общей стоимости операции, если стол или наковальня применили несколько зачарований сразу
- [ ] Согласовать извлечение проклятий, обработку самих зачарованных книг и предметов с модифицированным списком зачарований
- [ ] Если принят учёт стоимости, связать его с настоящими producer paths и запретить повторную компенсацию после снятия, переноса книги, копирования или повторного применения старой истории

**Критерий приёмки:** каждый клик снимает следующее зачарование в нужном порядке, выдаёт одну правильную книгу у точила и ровно утверждённую компенсацию. Отсутствие зачарований не меняет предмет и не создаёт награду

## 3. Обмен монет в Shipping Box

### Изменения по второму снимку

- Убрать зачёркнутый нижний ряд минус/поле/плюс слева и дублирование чисел
- Убрать постоянную надпись о выдаче монет в инвентарь и старый правый блок суммы с прежними кнопками
- Сохранить баланс, две колонки обмена, вкладку продажи и инвентарь
- Незачёркнутая строка получателя и перевода остаётся. Предложение: её сумма берётся из нового количества × выбранный номинал, перевод остаётся цифровым переводом Wallet
- Удалённые подписи и рамки убрать также из owning texture, если они запечены в PNG. Недостаточно спрятать только widgets

### Левая часть: физический размен

- [ ] Сохранить выбор исходного и целевого номинала из dropdown с настоящими иконками пяти монет
- [ ] Под исходной иконкой оставить одно редактируемое количество. При выборе исходного номинала оно автоматически заполняется доступным количеством таких обеспеченных монет в инвентаре
- [ ] Под целевой иконкой автоматически показывать только вычисленный результат. Ручное изменение результата не создаёт отдельную сумму операции
- [ ] Разрешить уменьшать исходное количество, не позволять подтверждать превышение реально доступных монет. Сервер повторно проверяет актуальный инвентарь и происхождение монет
- [ ] После обмена и изменения доступного количества обновлять обе стороны. Смена исходного номинала заполняет новый максимум, произвольный входящий snapshot не должен затирать незавершённый меньший ввод пользователя

Номиналы остаются 1 / 10 / 100 / 1 000 / 10 000 медных. Никакого нового курса или выпуска денег

**Предложение для неделимого остатка:** исходное поле показывает весь доступный максимум, операция меняет только полные группы и оставляет остаток в инвентаре. Например, из 17 Silver можно получить 1 Gold, списав 10 Silver и оставив 7 Silver. Подсказка подтверждения сообщает фактическое списание. Это выбранное при планировании предложение, поскольку пользователь не определил округление

Расчёт: `g = gcd(sourceValue, targetValue)`, `sourceStep = targetValue / g`, `targetStep = sourceValue / g`, `batches = floor(requestedCount / sourceStep)`. Списывается `batches × sourceStep`, выдаётся `batches × targetStep`. При нулевом результате подтверждение недоступно. Проверки вместимости и переполнения сохраняются

### Правая часть: точечное внесение и снятие

- [ ] Dropdown выбирает один номинал, соседнее цифровое поле задаёт число монет 1, 2, 3 и далее
- [ ] Действие "Внести" изымает ровно указанное количество выбранного номинала и зачисляет его стоимость в Wallet
- [ ] Действие "Снять" списывает `count × denomination.value` из Wallet и выдаёт ровно `count` монет выбранного номинала
- [ ] Нельзя дополнять нехватку другого номинала, вносить все остальные монеты или выдавать выбранную стоимость автоматической смесью номиналов
- [ ] Два действия используют один явно видимый выбор номинала и количества. Ошибка сообщает конкретную причину, не подменяя поля постоянной служебной надписью

## 4. Длинные пути bootstrap и падения с шейдерами

### Разделить три разных случая

- Bootstrap не может скачать или применить сборку из-за длинного полного пути Windows
- Сборка установлена, но шейдер не компилируется или падает при рендере
- У друга другие настройки или его личный overlay сохраняет старое значение

Пользователь указал историческую ошибку длинных путей и предположил связь текущих падений с непередачей настроек. Это направление расследования, не доказанная причина нынешнего падения

- [ ] Найти точную историческую поставку исправления `jem.9`, затем сопоставить с фактическим standalone bootstrap друга. Текущая локальная запись CHANGELOG уже описывает `jem.10`, но это не свидетельство его установки у друзей
- [ ] По существующему crash/latest/bootstrap логу установить стадию сбоя, имя шейдера, GPU/драйвер, точный путь и ошибку. Не смешивать MAX_PATH, shader compilation и общий сбой рендера
- [ ] Для проблемы пути проследить download → CAS → planner → projection → commit в `Mods/JEMBootstrap/patches/reliable-updates.patch` и подготовленном закреплённом upstream. Проверить фактическую provenance собранного JAR
- [ ] Предпочесть исправление нативного владельца длинных путей с сохранением containment, hash, trust и recovery. Не выдавать `no-shaders` JAR, отключение шейдеров или смену системной политики Windows за исправление полного контракта
- [ ] Для проблемы настроек сравнить canonical defaults с фактически активными файлами и native editable overlay. Не отправлять друзьям личный `options.txt`, аккаунты, пути, skin uploads или секреты
- [ ] Предложить переносимый профиль графики/шейдера через его существующего владельца. Для уже изменённых личных настроек нужен явный выбор применить общий preset, поскольку silent overwrite нарушает сохранение личного overlay

**Критерий приёмки:** установленная причина подтверждена конкретной стадией и артефактом, исправление достигает её владельца. Поставка не требует отказа от шейдеров ради обхода пути и не обещает поддержку шейдера на несовместимом GPU

## 5. Друзьям не приходят изменения сборки целиком

Это отдельное подтверждённое уточнение пользователя. Сохранение личных настроек само по себе не объясняет отсутствие новых модов, контента и исправлений

- [ ] Для одной конкретной отсутствующей правки установить её canonical source, свежий production artifact и SHA-256 в `Client/ManagedPack`
- [ ] Сравнить этот файл с тем, что реально опубликовано на используемом друзьями сервере, а затем с их installed active generation/token и JAR hash
- [ ] Отдельно установить, входят ли локальные изменения в уже разрешённый MineRENT release. Накопленные локальные изменения до такого release нельзя считать опубликованными друзьям
- [ ] Проследить цепочку `Client/ManagedPack → staged host source → native preview → publish → server advertised generation → friend route/bootstrap → download → native application → active token`
- [ ] Различить устаревший host pack, отсутствие публикации, иной remembered route, старый отдельный bootstrap, отказ trust gate, pending transaction, незавершённый helper после закрытия игры и старый активный процесс
- [ ] Исправлять первое подтверждённое неверное звено. Не raw-copy managed files, не редактировать active pointers и не ослаблять native trust
- [ ] Описать понятный пользователю recovery: какой matching bootstrap заменить отдельно и как штатно завершить нативное применение после закрытия Minecraft
- [ ] Если понадобится friend point-update, сформировать cumulative package из предыдущего актуального ZIP с override свежими managed файлами и полным `kubejs`, точными replace/add/delete инструкциями. Не создавать и не распространять его в текущем планировании

**Критерий приёмки:** конкретная правка прослеживается до активной установки друга по совпадающему содержимому. Наличие Download, опубликованного manifest или нового ZIP отдельно этого не доказывает

## Порядок будущей реализации и поставки

1. Сначала расследовать невидимый результат и отсутствующие обновления. Не смешивать их с предположением о синем экране или шейдерах
2. Утвердить открытые XP-правила и предложенные детали округления/перевода монет до реализации зависимых частей
3. Перед Java/config/gameplay изменениями выполнить canonical Atlas lookup и before-change impact scan. После изменений обновить `Catalog/changes`, effective index и выполнить предусмотренную Atlas validation, не создавать активную запись о ещё не реализованной механике сейчас
4. Реализовать части у перечисленных владельцев без новой денежной системы и без подмены native AutoModpack
5. Обновить соответствующие owning Docs, CHANGELOG и release evidence. Дефекты до пользовательской приёмки получают статус `in testing`, а не `resolved`
6. Собирать и синхронизировать необходимые артефакты только в рамках будущего запроса на реализацию. После managed changes выполнить standing native stage/preview/publish/application workflow для `test jem`, отдельно обновить standalone bootstrap там, где это потребуется
7. MineRENT, stable, friend release и baseline promotion остаются отдельной разрешённой границей поставки. Они не следуют автоматически из локальной реализации или этого плана

Автоматические тесты, fixtures и runtime QA этим планом не создаются и не разрешаются. Критерии выше описывают ожидаемый результат, они не являются заявлением о выполненных проверках
