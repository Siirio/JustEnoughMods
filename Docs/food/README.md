# Prepared-food quality and dietary variety

JEMCompat owns ordinary food quality on integrated and dedicated servers. The single assignment authority is [food-quality-assignments.json](../../Catalog/changes/food-quality-assignments.json), under Atlas change ownership. The build projects that exact file to `data/jemcompat/food_quality.json`; runtime never infers a tier from a mod name, item name or recipe complexity. [COVERAGE.md](COVERAGE.md) is the sorted human-readable projection, including installed JAR hashes, exact recipe evidence, assignments and exclusions.

There are 123 exact assigned IDs: 61 Tasty, 60 Exquisite and two Masterpiece. These cover a measured subset of six installed cooking modules. The report explicitly lists 129 other native recipe outputs that are excluded or unresolved. This is not a claim of complete edible coverage across every installed namespace. Runtime additionally requires native completed edible-item consumption, or the audited successful Kaleidoscope placed-food bite. Raw ingredients, ordinary bread and unclassified foods remain useful and do not clear a bundle.

## Behavior and ownership

Each qualifying consumption atomically replaces the previous food bundle. Tier I has one component for 0.4 Minecraft days; II has two for 0.75 days; III has three for 1.5 days. These are the requested exact native durations; internal storage and calculations remain in engine units. Every component uses a verified vanilla effect ID and the approved family matrix. Native hunger, saturation, built-in food effects, quality NBT, recipes, JEI discovery, containers and remainders remain with their original mods. Existing native food effects are independent sources and may increase the total visible effects beyond the JEM bundle's component count.

`FoodEvents` alone inserts effects on server players after `LivingEntityUseItemEvent.Finish`. `KaleidoscopeFoodBiteMixin` adapts Cookery 1.4.1's native `FoodBiteBlock.eat` successful return, which occurs only after native hunger, effects, portion mutation and container behavior. It uses the actual source block's registry ID. Native failure/pass and client prediction award nothing. The source operation is never canceled or replaced. This also covers installed addon foods registered through Cookery's `FOOD_DATA_MAP` and `CommonRegistry.onBlockRegistryEvent`, whose items are genuine `BowlFoodBlockItem` instances rather than fields in `ModItems`.

Vanilla exposes one active instance per effect ID with a source-blind hidden chain. JEM therefore uses a deliberately conservative collision rule:

- If an independent same-ID instance already exists, JEM leaves it completely untouched, including a weaker/shorter instance. The food component waits while its bundle lifetime continues decreasing. Once that independent effect naturally ends, food may insert only its remaining lifetime.
- A narrowly scoped `LivingEntity.addEffect(MobEffectInstance, Entity)` HEAD hook removes an exact JEM-owned instance before vanilla caches the old instance for merging an external insertion. The external input then follows native applicability and merge rules. `MobEffectEvent.Added` is unsuitable: installed Forge posts it after caching the old instance. `Applicable` is unsuitable because it also fires from non-insertion `canBeAffected` queries.
- JEM never snapshots, restores, extends or resets an external effect or its hidden chain. Rejected external insertion may briefly detach food; the next native player pulse resumes only the existing remaining lifetime. If another mod cancels removal, JEM relinquishes ownership and treats the surviving instance as external.
- Bundle replacement and expiry remove only the exact object that JEM inserted. Milk/ordinary removal marks the bundle cleared durably and finishes cleanup on the next safe player pulse, avoiding mutation during vanilla's active-effect iteration.

This provides safe source separation for the audited native `addEffect` route. It does not provide general source tracking for mods using `forceAddEffect`, direct active-effect map/instance mutation, raw attribute edits, or direct absorption writes while JEM owns absorption. Those routes bypass the audited hook and require specific native adapters before stronger compatibility claims. A food component may be temporarily absent while an independent effect occupies the same ID; tooltip lists the intended bundle, not a promise that an independent source is overridden.

## Absorption and persistence

The installed `AbsoptionMobEffect` adds full capacity on insertion and subtracts full capacity on removal. Recreating it naively refills hearts. JEM records spent food absorption and a durable active-player-time budget window. Damage observed while food owns absorption consumes that allowance. Replacing food, eating an intervening non-absorption dish, relogging or dying does not reset it. A new insertion receives only `max(0, tier capacity - spent allowance)`. No periodic refresh occurs, and raw absorption without an active effect defers food insertion because that scalar has no general source ownership.

Schema 1 lives in the player's Forge persistent data under `JemFoodQualityV1`: bundle ID/remaining duration, exact owned-instance serialization fingerprints, pending clearing flag, absorption budget/debt and per-ID meal timestamps. No external-effect snapshot is stored. Native effect serialization remains native. Reconnection reclaims ownership only if the complete fingerprint matches, allowing at most the single native decrement between the Forge player pulse and native save; unknown effects are treated as external. Native logout preserves remaining duration; no insertion/refill is performed on login. Server stop clears process-local identities. Actual death clears the bundle; the normal clone hook retains minimal dietary timestamps and spent absorption debt. There is no prior JEM food schema to migrate.

## Dietary variety and presentation

Five distinct assigned registry IDs within the previous three Minecraft days of active server time grant one stable +5% movement-speed `MULTIPLY_BASE` modifier, UUID `766d2410-48f2-4223-bc78-d23860a9e004`. Repeated consumption refreshes the one timestamp for that ID. A threshold loss removes the modifier once; there are no tiers, stacking or penalties. Timestamp expiry uses the overworld's native `gameTime`, which advances with active server simulation and is independent of `dayTime`, sleeping and `/time set`. Offline players' dietary timestamps age while the server continues running; stopped-server wall time does not advance them. Player pulse work is limited to that player's curated timestamps and at most three components, with no entity/chunk/world scan or forced loading.

The read-only `jemcompat:food` channel sends only dietary count changes, login and clone state to the client. No food mutation packet exists. Client tooltips show localized quality, exact native effect names/Roman levels, durations in Minecraft days, replacement behavior, progress and the active movement bonus. Separate language resources are `assets/jemfood/lang/en_us.json` and `ru_ru.json`; they merge through Minecraft's normal language loading. There is no dietary GUI or persistent HUD.

## Evidence and verification limits

Installed recipe JSON and item registration bytecode were inspected for Bakery 2.0.6, Farm & Charm 1.0.14, Brewery 2.0.6, Kaleidoscope Cookery 1.4.1, Kaleidoscope Nether 1.1.8 and Kaleidoscope End 1.0.14. Other inspected cooking modules and coverage boundaries are identified in the report. Cookery native `FoodBiteRegistry`, `CommonRegistry`, `FoodBiteBlock.eat`, `BowlFoodBlockItem`, Forge 47.4.10 effect events, mapped `LivingEntity.addEffect` and native absorption modifier bytecode establish the extension seams. Exact-ID Atlas/research queries supplement those installed sources; Atlas's static inference is not described as live Forge registration proof.

No automated tests, gameplay launches, linters or static-analysis jobs were added or run for this feature. Source review is not player acceptance. Production packaging, ordinary local synchronization, Atlas rebuild/validation and native AutoModpack publication are coordinated by the parent task under the repository's standing delivery rules. A new client-facing network channel requires matching fresh JEMCompat on both logical sides; do not call this a server-only update.
